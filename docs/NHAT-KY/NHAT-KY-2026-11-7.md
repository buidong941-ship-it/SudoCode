## 1. Ý tưởng & Thiết kế kiến trúc "LLM chọn hàm, Code thực thi"

### 1.1 Đặt vấn đề
> **Câu hỏi trao đổi:**  
> *"Sẽ ra sao nếu tôi định nghĩa rõ ràng các hàm rồi đưa LLM như Jev để nó bỏ phiếu nên chọn hàm nào chuẩn hơn? Sau khi chọn hàm rồi thì mình sẽ có bước gọi code xử lý. Mình sẽ quy định trong 1 file `.json` là khi gọi hàm nào sẽ xử lý thế nào, rồi chỉ cần bê vào code để cho nó gọi?"*

**Đánh giá:** Hướng này hoàn toàn khả thi và hợp lý. Nó chính là mẫu *"LLM chọn hành động, code thực thi"*, khớp với kiến trúc hiện có (`harness/planner_rules.json` đã là một bảng JSON ánh xạ điều kiện sang hàm xử lý `do → h_order_change`, `h_order_status`...).  
Điểm khác biệt cốt lõi: Thay vì dùng **regex** để chọn dòng, ta dùng **LLM** để chọn hàm.

### 1.2 Luồng xử lý đề xuất mỗi lượt

```
Lời khách + ngữ cảnh
  → Router (intent, cờ an toàn)                    [giữ nguyên]
  → Code lọc các hàm HỢP LỆ ở trạng thái hiện tại  (vd: không có đơn thì loại "đổi địa chỉ đơn")
  → Jev/Qwen bỏ phiếu: hàm nào khớp lời khách     (có/không + độ tin cho từng hàm)
  → Code kiểm điều kiện của hàm được chọn          (thiếu địa chỉ → chuyển sang hỏi địa chỉ)
  → Code gọi hàm xử lý theo file JSON              (điền tham số từ slot, bộ nhớ, tool)
  → Goal + FACTS → Generator
```

Phác thảo một mục trong file JSON định nghĩa hàm (`functions.json`):

```json
{
  "update_order_address": {
    "description": "Khách muốn đổi địa chỉ giao hàng của một đơn ĐÃ ĐẶT",
    "available_if": ["has_open_order"],
    "requires": ["slot:address"],
    "on_missing": {"slot:address": "ask_address"},
    "args": {
      "order_id": "memory.open_order_id",
      "address": "slot.address"
    },
    "handler": "h_update_address",
    "goals": ["address_updated"],
    "examples": {
      "yes": ["em đổi giúp chị sang 5 Bạch Đằng nhé"],
      "no": ["giao về đâu vậy em?"]
    }
  }
}
```

Danh sách hàm dự kiến khoảng 15 mục: `quote`, `add_to_cart`, `create_order`, `update_order_address`, `exchange_size`, `return_order`, `order_status`, `schedule_callback`, `policy_answer`, `competitor_reply`, `refuse_internal`, `identify_customer`, `handoff`, `ask_repeat`, `closing`...

### 1.3 Ưu điểm (Cái được)

- **Hiểu cách nói đa dạng:** Giải quyết đúng loại lỗi của holdout v3: `"cho giao về X"` là đổi địa chỉ, `"lấy Combi Sugocal"` là đổi sản phẩm, `"thêm X"` khác `"lên đơn"`. Regex hỏng ở đúng những chỗ này; mô hình phân loại của LLM làm tốt hơn nhiều.
- **Tham số do code điền tất định:** Bộ chấm đòi `args_match` chính xác; LLM không trực tiếp sinh tham số nên không lo bịa mã đơn hay giá.
- **Dễ đọc, dễ giải thích và gỡ lỗi:** File JSON liệt kê rõ ràng hành vi và điều kiện. Trace ghi lại rõ model chọn hàm nào với độ tin bao nhiêu.
- **Phù hợp với cơ chế của Jev:** Jev vốn là bộ phân loại dạng Choice có kèm điểm tin cậy (tương tự như cách `jev_hybrid.labels()` đang dùng).

### 1.4 Các điểm phải thiết kế kỹ

1. **LLM chỉ sửa lỗi chọn sai hành động, không sửa lỗi logic nghiệp vụ bên trong hành động:**  
   Các lỗi sau vẫn bắt buộc phải xử lý trong code của hàm:
   - Hạn đổi trả theo ngày đơn (gốc lỗi 1);
   - Tổng giỏ trên 10 triệu thì không nhận COD;
   - Dời lịch khi rơi vào ngày nghỉ, đọc "9 rưỡi" (gốc lỗi 6);
   - Câu trả lời thiếu cụm bắt buộc (phía generator).  
   *Áp vào 26 ca trượt holdout v3:* Hướng này giải quyết tốt gốc lỗi 2, 3, 4 (~12 ca) và một phần gốc lỗi 5. Phần còn lại vẫn cần sửa code logic.
2. **Một lượt có thể kích hoạt nhiều hàm:**  
   Ví dụ: *"thêm X nữa, tổng bao nhiêu em?"* cần cả `add_to_cart` + `cart_total`. Cần cho model bỏ phiếu đa nhãn (có/không cho từng hàm), không ép chọn duy nhất 1 hàm, kèm quy tắc thứ tự thực thi trong JSON.
3. **Quy tắc phân xử bất đồng giữa luật và LLM:**
   - **Nhóm an toàn** (nội bộ, bảo mật khách khác, AI hay người, xóa dữ liệu, xác định danh tính): Giữ luật và cờ router, LLM không được quyền bác bỏ.
   - **Nhóm nghiệp vụ** (giỏ hàng, đơn hàng, đổi trả, địa chỉ): LLM quyết định chính, luật làm dự phòng.
   - Khi độ tin cậy thấp hoặc LLM lỗi thì fallback về luật. Ngưỡng độ tin cậy cần cố định trước (như router đang dùng 0,45).
4. **An toàn trước jailbreak:** Các hàm nhạy cảm (`forget_customer`, tra đơn) phải có điều kiện cứng trong code (ví dụ: chỉ lấy số điện thoại từ cuộc gọi đến theo bài học J6). Dù LLM có chọn hàm thì code vẫn chặn nếu không thỏa điều kiện.
5. **Độ dao động:** Cần ngưỡng tin cậy và lưu trace chi tiết khi model ở ranh giới quyết định.
6. **Chi phí token và độ trễ (Latency):** Gọi Jev với ~15 câu hỏi mỗi lượt tốn rất nhiều token. Cần cân nhắc chỉ gọi ở các lượt có khả năng thay đổi đơn/giỏ (10–20% số lượt), hoặc dùng Qwen3-4B local.
7. **Khối lượng công việc:** Cần viết lại lớp chọn, file JSON mô tả hàm và điều kiện, sau đó đo lường lại toàn bộ trên các tập test.

## 3. Thiết kế luật ràng buộc giữa các hàm (Prompt & Code Rules)

### 3.1 Đặt vấn đề & Định hướng

- Trên các ca khó (phần C), Qwen hơn luật rõ: **80,9** so với **71,3**.
- Trên ca thường (phần A), Qwen vẫn kém luật xa: **79,4** so với **96,8**.
- Khoảng 2/3 lỗi của Qwen do mô tả hàm chồng nhau (`place_order` / `give_delivery_info`: 18 lần; câu hỏi chính sách bị hiểu nhầm là thao tác đơn: 11 lần).

Giải pháp là đặt luật ràng buộc ở 2 tầng với vai trò riêng:

1. **Tầng 1: Luật cứng trong file JSON (Code thực thi sau khi LLM chọn):**  
   Code luôn chạy đúng 100%, độc lập với việc model có tuân thủ prompt hay không.

```json
{
  "place_order": {
    "requires": ["product_chosen"],
    "on_missing": {"address": "ask_address", "payment": "ask_payment"}
  },
  "give_delivery_info": {
    "implies_if": {"not has_order": "place_order"}
  },
  "add_to_cart": {
    "conflicts": ["place_order"],
    "unless": "close_cue"
  },
  "change_order_address": {
    "requires": ["has_order", "slot:address"]
  },
  "exchange_order": {
    "requires": ["has_order"],
    "conflicts": ["policy_question"],
    "unless": "not question_form"
  }
}
```

**Chi tiết các loại luật cứng:**

| Loại | Ý nghĩa | Ví dụ thực tế (từ lỗi của probe) |
|---|---|---|
| `requires` | Thiếu điều kiện thì không chạy hàm, chuyển sang hỏi | `place_order` cần sản phẩm đã chọn; thiếu địa chỉ thì gọi `ask_address` |
| `implies` | Chọn A thì bắt buộc kéo theo B | `give_delivery_info` khi chưa có đơn thì kéo theo `place_order` (sửa 18 lỗi) |
| `conflicts` | A và B không đi cùng nhau | `add_to_cart` và `place_order` cùng xuất hiện mà không có tín hiệu chốt thì giữ `add_to_cart` |
| `on_missing` | Thiếu slot thì gọi hàm khác trước | `change_order_address` khi chưa có slot `address` thì hỏi lại địa chỉ |

2. **Tầng 2: Vài luật ngắn trong Prompt (Để LLM chọn đúng từ đầu):**  
   Dành cho các trường hợp phải hiểu nghĩa câu mà code không làm được:
   - Câu dạng hỏi (*"được không"*, *"mấy ngày"*, *"có mất phí không"*, *"bao lâu"*) về quy định thì là `policy_question`, dù có nhắc tới đơn của khách (sửa 11 lỗi chính sách).
   - *"Lấy / đặt / chốt + tên sản phẩm"* là `place_order`.
   - *"Thêm / nữa"* mà chưa bảo lên đơn là `add_to_cart`.
   - Khách vừa đưa địa chỉ hoặc cách thanh toán khi chưa có đơn nghĩa là đang đặt đơn mới.

*Lưu ý:* Chỉ nên giữ khoảng 3–5 luật. Model 4B làm theo danh sách luật dài khá kém, và prompt dài còn làm tăng độ trễ (latency vốn đang ở mức 12,7 s).

### 3.2 Luồng xử lý đề xuất

```
Lời khách
  → Qwen chọn hàm (Prompt có mô tả đã sửa + 3–5 luật ngữ nghĩa)
  → Code áp requires / implies / conflicts / on_missing từ JSON
  → Code gọi hàm xử lý
```

**Rủi ro cần lưu ý:**
- Các luật trên rút ra từ chính lỗi của probe. Cần thêm tập câu mới (bộ D) viết trước khi xem kết quả lần sau để kiểm định khách quan.
- Luật cứng sửa được lỗi kết hợp hàm, không sửa được lỗi hiểu sai ý (ví dụ chọn nhầm `ask_price` cho câu chốt đơn).

*(Ghi chú: `action` = chọn đúng hàm thay đổi trạng thái; `exact` = chọn đủ và không thừa hàm nào).*

### 4.3 Phân tích & Đánh giá kết quả

1. **Sửa mô tả hàm và thêm 5 luật trong prompt mang lại tác dụng lớn:**
   - Tập A tăng từ 79,4% → **95,2%**;
   - Tập D (câu mới) tăng từ 88,0% → **92,0%**;
   - Độ đúng đầy đủ (`exact`) trên D tăng từ 68,0% → **78,0%**.
2. **Luật cứng trong code gần như vô ích:**
   Chỉ sửa được 1 mục nhưng lại làm hỏng 2 mục:
   - `V3-058 t1`: Qwen chọn thừa `give_delivery_info` cho câu không có địa chỉ, luật kéo theo `place_order` nên thành tạo đơn sai;
   - `D-49`: Tương tự, ở câu khách đòi thông tin của người khác.  
   *(Khuyến nghị: Nên bỏ luật `implies` này, hoặc chỉ áp khi câu thực sự có trích xuất được địa chỉ hay thanh toán).*
3. **Đóng góp của Router Jev:** Luật thuần yếu hơn hệ thống hiện tại khoảng 10 điểm (A: 87,3 so với 96,8; C: 61,7 so với 71,3) — đây chính là phần đóng góp chất lượng của router Jev.
4. **Hiệu quả theo nhóm ca khó trên tập D (Qwen bản 2 vs Luật thuần):**

| Nhóm ca khó | Luật thuần | Qwen bản 2 |

### 4.4 Các lỗi còn tồn đọng của Qwen Bản 2

- **Chọn nhầm sang `greeting_closing` (7 lần):**
  - Câu đầu cuộc gọi kiểu *"Em ơi, chị lấy Joie Pact như hôm trước nói nhé"* (`V3-027…030`);
  - Câu hẹn gọi lại *"Chiều thứ sáu khoảng 4 giờ em gọi lại cho chị"* (`D-28`, `D-29`).  
  *Nguyên nhân:* Luật số 5 trong prompt (*"xác nhận ngắn, cảm ơn, chào → greeting_closing"*) đang bị áp quá rộng.
- **Bỏ sót hàm phụ (3 lần):** *"Lấy thêm X, cái này bao nhiêu?"* chỉ ra `ask_price`, thiếu `add_to_cart`.
- **Lỗi nhận diện cá biệt:** *"Nhận lại hàng"* hiểu thành hủy đơn (`D-03`), *"Lấy cho cô cái quạt tháp"* hiểu thành hỏi giá (`D-38`).

### 4.5 Những điểm cần lưu ý

- **Độ trễ (Latency):** Vẫn ở mức cao ~**12,5 s** mỗi lần chọn hàm (p95 ~**14,6 s**). Bản 2 ngắn hơn ở mô tả nhưng lại thêm prompt luật, nên không cải thiện tốc độ. Nếu tích hợp nguyên trạng vào agent thì Total p95 sẽ vượt xa ngưỡng 8 s.
- **Độ tin cậy của tập kiểm thử:** Phần D do tác giả viết sau khi đã biết các loại lỗi và chỉ có 50 câu, nên kết quả vẫn mang phần lạc quan. Còn các tập A, B, C đã được quan sát trong quá trình sửa bản 2.
- **Khoảng cách đến TSR:** Probe chỉ mới đo lường việc chọn đúng hàm, chưa đo TSR. Việc chọn đúng hàm là điều kiện cần; code thực thi bên trong hàm (như tính hạn đổi trả theo ngày đơn) vẫn bắt buộc phải chính xác.
